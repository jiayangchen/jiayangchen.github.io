编程 Agent 的长会话，往往先遇到上下文容量问题。读过的文件、执行过的命令、测试日志、修改记录和用户补充的要求，会不断进入后续请求。一个任务还没有完成，历史消息就可能已经挤满模型窗口。

直接删除最早的消息很容易，但最早的消息里可能恰好包含用户目标、禁止事项，以及某个设计为什么被否决。只留下最近的代码和日志，Agent 仍然能继续输出，却可能已经偏离原来的任务。

Claude Code（下文简称 CC）和 Pi 都通过上下文压缩解决这个问题：用摘要承接较早的历史，同时保留继续工作所需的信息。两者的侧重点有所不同：CC 的公开分析展示了一套与缓存、工具输出、运行时状态协同的分层机制；Pi 的工程文章则把流程集中在“保留近期消息、独立总结旧历史、重新组成上下文”上。

> 资料范围：本文整理自文末三篇文章，未独立审计对应版本源码。CC 的两篇第三方分析对层级划分、Microcompact、Context Collapse 和 token 计数存在分歧，文中会明确归属。Pi 部分依据 Earendil 工程团队于 2026 年 8 月 13 日发表的说明。具体阈值应结合版本和配置理解。

## 1. 压缩的对象，是下一次请求中的工作上下文

一次编程会话发送给模型的内容，可以简化为：

```text
系统提示词 + 工具定义 + 项目说明 + 历史消息 + 工具结果 + 当前请求
```

模型返回工具调用后，Agent 执行工具，再把结果放进下一次请求。随着工作推进，这串内容持续增长。

压缩后，请求通常变成：

```text
系统提示词 + 工具定义 + 历史摘要 + 最近的消息 + 当前请求
```

这里需要区分两个概念：消息是否仍保存在会话存储中，以及消息是否继续进入模型的活跃上下文。把旧内容移出请求，不一定意味着删除磁盘上的原始记录；保留原始记录，也不意味着模型还能直接看到它。

压缩的效果因此不能只用“减少了多少 token”评价。更关键的是，模型能否继续回答这些问题：用户最终要什么，哪些事情不能做，已经改了哪些文件，验证到哪一步，下一步还缺什么。

## 2. Claude Code：在完整摘要之前，先处理上下文中的不同负担

两篇 CC 分析都强调了分层处理，但并没有给出一致的“五级流水线”。HarrisonSec 将工具结果预算、History Snip、Microcompact、Context Collapse、Autocompact 列为五层；Inside Claude Code 则将 Microcompact、Snip、Collapse、Auto Compact、Reactive Compact 列为五层。[1][2]

因此，更适合按各个机制解决的问题理解 CC，而不是把两篇文章拼成一条精确的固定调用链。

### 2.1 先控制工具输出，避免一次调用占满窗口

很多上下文压力来自工具结果：一个大文件、一轮构建日志，或者一次范围过宽的搜索，都可能比用户消息大得多。

HarrisonSec 描述的处理方式是：工具结果超过 50,000 字符时，把完整输出写入磁盘，在上下文中保留约 2KB 预览和文件路径。后续有需要，再通过读取工具找回具体内容。[1]

Inside Claude Code 还介绍了 BashTool 的 `tokenSaverOutput`：用户界面展示完整输出，而模型接收压缩后的版本。[2]

两种描述共同指向一个设计原则：完整信息的保存，与每轮请求的信息携带，可以分开处理。模型通常不需要在之后的每一步都重新看到整份测试日志，但需要知道日志在哪里，以及当前值得关注的结果是什么。

### 2.2 清理旧历史时，同时考虑缓存

Snip 用于将较早或冗余的内容移出活跃上下文。两篇文章对它具体裁剪什么、如何归档的描述不同，但都将其放在完整 LLM 摘要之前。

Microcompact 的分歧更明显。

按照 HarrisonSec 的分析，它会根据提示词缓存状态选择两条路径：[1]

- **缓存已冷却**：直接修改旧工具结果，把可清理的内容替换为占位符，保留最近的一部分结果。
- **缓存仍然有效**：使用 API 层的 `cache_edits` 处理旧工具结果引用，尽量保护已缓存的前缀；编辑指令随后续请求发送，无需单独调用摘要模型。

Inside Claude Code 则把 Microcompact 描述成缓存布局优化：把易变内容移到后面，提高稳定前缀的复用率，并明确称其不减少对话体积。[2]

这两个描述无法直接视为同一种算法。它们可以支持的共同结论是：CC 的轻量处理会关注缓存，修改历史内容的收益需要与缓存失效的成本一起衡量。

### 2.3 Context Collapse：尝试保留更多原始细节

Context Collapse 位于完整摘要之前，但两篇资料对实现也有不同解释。

HarrisonSec 将其描述为可逆的投影视图：原始消息仍然保留，折叠信息存放在独立存储中，发送请求时由 `projectView()` 生成模型实际看到的内容。该文还指出，启用 Collapse 时会抑制 Autocompact，避免后者破坏前者希望保留的细粒度历史。[1]

Inside Claude Code 将其描述为分段摘要：识别调试、编辑、评审等逻辑片段，随着容量压力增加，逐步总结较早的片段。[2]

两者都强调渐进处理。至于摘要如何产生、是否需要额外模型调用、具体如何回滚，不能仅凭这两篇文章给出统一实现结论。

### 2.4 最后进行完整摘要，把历史交接给后续执行

当轻量处理不足以维持上下文预算时，CC 会进行 Autocompact。两篇资料都描述了派生子 Agent 生成结构化摘要的方式。[1][2]

Inside Claude Code 进一步指出，`runForkedAgent()` 派生的摘要 Agent 使用父 Agent 的模型，并复用其提示词缓存前缀。[2] 这种设计可以降低摘要请求重复处理长前缀的成本。

摘要模板覆盖九类信息：

1. 用户的主要请求和意图；
2. 关键技术概念；
3. 文件与相关代码；
4. 错误及修复；
5. 问题解决过程；
6. 用户消息；
7. 待完成任务；
8. 当前工作；
9. 下一步。

两篇文章都提到，摘要请求输出分析草稿与正式摘要两个区块，运行时通过 `formatCompactSummary()` 移除草稿，只把正式摘要带入后续上下文。

这份摘要更接近工程交接记录。它需要解释某个修改为什么存在、哪些尝试已经失败、还有哪些条件没有满足。只有“讨论了认证逻辑，修改了几个文件”这样的概括，很难支撑下一轮可靠执行。

### 2.5 压缩之后，重新补齐运行时状态

历史摘要并不能替代所有运行状态。正在使用的技能、当前计划、可用工具、最近关注的文件，都可能需要重新提供。

HarrisonSec 描述了压缩后的恢复步骤：补回最近读取的文件、已启用技能、延迟工具、Agent 列表与 MCP 指令，并恢复计划模式等状态。[1]

Inside Claude Code 则更系统地介绍了 `system-reminder`：将计划变化、文件修改、Hook 结果、预算压力、技能和工具变化等信息，按条件注入消息流。状态稳定时使用简短提醒，关键变化或压缩之后使用更完整的提醒。[2]

因此，CC 的连续性由两类信息共同支撑：摘要保存此前发生了什么，运行时提醒提供现在是什么状态。恢复工作时，两者都重要。

### 2.6 自动恢复必须有终点

预估容量仍然可能出错。工具突然返回大量内容，或请求中的其他部分增加，都可能使 API 拒绝请求。

Inside Claude Code 描述了针对上下文过长错误的 Reactive Compact，并使用 `hasAttemptedReactiveCompact` 限制单条恢复路径的重复尝试。[2] HarrisonSec 则介绍了自动压缩连续失败三次后停止的熔断机制。[1]

它们分别约束不同的失败路径，不能合并成“CC 所有压缩都只重试三次”。共同的工程要求是：恢复过程本身也要受预算约束，不能因为上下文太长而陷入无限摘要、无限失败的循环。

## 3. Pi：保留近期工作，为旧历史写一份交接摘要

Pi 的工程文章描述了一条更直接的路径：[3]

1. 正常对话持续追加消息。
2. 一轮交互结束后，检查是否接近上下文容量上限。
3. 按 token 预算保留最近的一段消息。
4. 提取更早的历史，序列化后交给独立摘要请求。
5. 将摘要作为压缩记录追加到会话。
6. 使用摘要和原样保留的近期消息继续工作。

用户也可以通过 `/compact` 手动触发压缩；如果轮次进行中遇到上下文溢出，Pi 可以中途压缩。

### 3.1 以轮次结束作为常规检查点

一次用户请求可能包含多次模型调用和工具执行。只要这一轮还在正常进行，请求就继续扩展原有前缀，能够利用已有缓存。

Pi 在轮次结束后检查自动压缩条件，使常规压缩发生在一个相对自然的工作边界。上下文溢出则作为例外处理，允许打断这一节奏。

### 3.2 按 token 预算保留近期消息

Pi 不固定保留“最后十条”或“最后十轮”，而是使用可配置的 token 预算。文章给出的默认值为 20,000 token，大致相当于 5～20 轮交互。[3]

这是因为消息长度差异很大。一轮只有简短问答，另一轮却可能包含大量工具输出，按条数保留无法稳定控制体积。

保留区域之前的历史会被提取并总结；近期区域原样留存。这样，远期历史承接目标和决策，近期消息则保留当前调试所需的精确细节。

### 3.3 使用独立的摘要请求

Pi 为压缩构造专门请求，系统角色从“编程助手”切换为“上下文摘要助手”，要求模型为之后继续工作生成结构化交接说明，重点包含目标、进展和关键决策。[3]

这里的“独立”不表示摘要器看不到历史。旧消息会作为待总结材料提供，只是不沿用正常编程对话的系统提示词和请求组织方式。

这个边界让摘要模型可以独立选择。Pi 的文章指出，该请求可以使用不同模型；这表示实现具有这种能力，并不代表默认一定使用更便宜的模型。

### 3.4 纯文本摘要支持后续模型切换

Pi 将压缩结果以纯文本形式存入会话。继续执行时，请求由系统提示词、工具、摘要、近期消息和新用户消息重新组成。

纯文本便于阅读，也便于在切换模型后继续使用。模型不需要理解专有的隐藏状态，就能读到此前任务的交接记录。

Pi 还允许通过扩展替换压缩机制。需要不同的交接格式时，可以定制摘要提示词，例如更强调测试结果、未解决假设或业务约束。

## 4. 缓存：压缩节省了空间，也改变了前缀

提示词缓存通常要求前缀精确匹配。某段文本本身没有改变，并不意味着它一定还能命中旧缓存；它前面的内容也必须满足复用条件。

Pi 的文章对此给出了清楚的解释：[3]

```text
压缩前：系统 + 工具 + 旧历史 + 近期消息
压缩后：系统 + 工具 + 摘要   + 近期消息 + 新消息
```

从旧历史被摘要替换的位置开始，前缀发生变化。近期消息虽然原样保留，但因为前面的内容变了，其旧缓存状态也不能直接复用。稳定的系统和工具前缀仍可能复用，之后的内容需要重新计算；随后的请求再逐步形成新缓存。

CC 的分析则展示了更多缓存协同手段：轻量阶段尽量保护稳定前缀、将动态提醒与静态内容分开，以及在完整摘要请求中复用父 Agent 的模型和前缀。[1][2]

需要区分的是，**摘要请求复用了缓存，不等于压缩后的主会话仍能复用全部旧历史缓存**。后续请求是否命中，仍取决于重新组织后的实际前缀。

对系统设计者来说，合理目标是综合评估摘要调用成本、缓存重建成本、后续请求节省的 token，以及信息损失造成的返工。仅靠“越早压缩越省钱”无法指导所有场景。

## 5. 两种实现的对照

| 维度 | Claude Code：据两篇公开分析 | Pi：据工程团队说明 |
|---|---|---|
| 整体路径 | 多种轻量处理与完整摘要协同 | 保留近期历史，独立总结旧历史 |
| 大型工具输出 | 描述了落盘预览、模型侧输出压缩等措施 | 本篇文章未展开相关机制 |
| 近期历史保留 | 资料涉及近期消息保留及压缩后文件恢复，具体策略依描述而异 | 可配置 token 预算，文章默认值为 20K |
| 摘要执行 | 派生子 Agent；其中一篇描述为继承父模型并复用前缀 | 独立摘要请求，可以选择不同模型 |
| 摘要结构 | 用户意图、文件、错误、待办等九类信息 | 强调目标、进展与关键决策 |
| 状态连续性 | 摘要之外，配合技能、计划、工具和系统提醒恢复 | 文章重点是摘要与原样保留的近期消息 |
| 缓存取舍 | 在轻量处理、摘要请求和动态状态注入中考虑缓存 | 轮末检查；明确接受替换历史后相应前缀缓存需要重建 |
| 异常处理 | 资料描述了被动压缩保护及连续失败熔断 | 上下文溢出时可在轮次中途压缩 |
| 定制方式 | 这两篇资料没有以自定义压缩扩展为重点 | 可以通过扩展替换压缩机制与提示词 |

这些差异也反映了文章范围：CC 两篇文章讨论了更多外围机制，Pi 的文章聚焦压缩主流程。不能据此断言 Pi 没有其他上下文优化，或 CC 缺少其他定制能力。

## 6. 对编程 Agent 设计的启发

### 6.1 把摘要当成交接契约

好的摘要应该足以支持接班者开始下一步，而不只是概括上一班做过什么。

例如，“修复了登录问题”不如“已修改 token 过期判断；刷新失败重试尚未实现；单元测试通过，集成测试因测试账号失效未执行”有用。后者同时保留结果、边界和未完成事项。

CC 的结构化模板和 Pi 的交接思路，都可以用这个标准评价。

### 6.2 对不同信息采用不同保留方式

大量原始日志适合外置后按需读取；旧的探索过程适合摘要；当前错误和近期修改需要更高保真；计划、工具能力和权限状态适合由运行时维护。

这些内容对后续决策的作用不同，采用单一的“删除最旧消息”规则，很难兼顾容量和正确性。

### 6.3 保留来源与指令边界

摘要需要分清用户要求、工具输出、文件内容，以及 Agent 自己的推断。

如果把文件里出现的一段文字总结成“用户要求”，压缩就改变了它的权限语义。HarrisonSec 专门讨论了恶意文件内容可能在摘要中延续的问题。[1] 因此，交接记录还应保留重要结论的来源，避免把不可信内容升级为指令。

### 6.4 用任务连续性验证压缩效果

验证压缩，除了检查体积，还应该检查压缩前后行为是否一致。例如：用户禁止修改的目录是否仍被记住，已经失败的方案是否被再次尝试，尚未完成的测试是否被误写成通过，当前计划能否接续。

这些是根据两种设计推导出的实践建议，而非三篇文章已经提供的统一测试方案。

CC 展示了通过多种机制共同管理长会话的思路，Pi 展示了清晰、可定制的摘要边界。它们共同说明：上下文容量管理最终要服务于任务连续性。释放空间只有在 Agent 仍然知道目标、约束和下一步时，才真正有价值。
